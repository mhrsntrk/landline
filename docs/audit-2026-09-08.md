## Findings

### 1. P1: concurrent unlocks bypass the global attempt budget and backoff

**Location:** `crates/landlined/src/auth.rs:162-195`, especially the check before `spawn_blocking`.

`verify()` checks lockout and reads `not_before`, then releases the state lock before hashing. Multiple HTTP token requests or WebSocket unlocks can all pass these checks before any result records a failure. Requests already waiting on the same deadline also resume together without rechecking lockout. Every admitted request reaches Argon2, even after other requests exhaust the ten-attempt budget. A successful in-flight request can reset a lockout established by other requests.

**Observed:** 12 simultaneous wrong secrets against the real `UnlockGate` produced 12 recorded failures in a single batch. Both reproduction tests finished in 0.65 seconds combined. The existing tests cover expired and active lockouts, but not concurrent admission.

**Impact:** the promised ten guesses per cooling window is not enforced; callers who reach the unlock stage can also multiply CPU and memory consumption before knowing the secret. This includes local callers under the repository's documented loopback threat model.

**Fix:** serialize admission, the backoff check, verification, and state update with an async gate or equivalent reservation mechanism shared by HTTP and WebSocket callers. Recheck deadlines and lockout after waiting. Keep failure arithmetic bounded. Test simultaneous wrong attempts and a correct attempt racing the tenth failure.

### 2. P1: background polling can lock out a manually unlocked host

**Location:** `ios/Landline/UI/TerminalScreen.swift:749-766` and `1047-1052`; `ios/Landline/Net/HostAPI.swift:245-287`.

The manual unlock prompt sends the typed secret to the WebSocket and immediately clears it. `refreshOffers()` separately reads the Keychain, substitutes an empty string when no secret is stored, and suppresses every error. Its polling loop repeats while the shell is live. A wrong Keychain secret is equally problematic: the user can manually correct the shell unlock while HTTP continues using the old secret.

**Trigger:** configure a daemon unlock secret, leave the phone's stored secret empty or stale, open the terminal, and enter the correct secret in the manual prompt. Outbox polling repeatedly submits the empty or stale secret to `/v1/token`. Failed mints create no cache entry, so later polls mint again. The HTTP and WebSocket gates share the same daemon-wide failure budget.

**Impact:** normal use silently spends the failure budget and can prevent the next reconnect for 15 minutes. The active shell initially continues working, hiding the cause. The API's 20-second timeout does not make a failed attempt safe to repeat.

**Evidence:** confirmed through the complete polling, credential, token-cache, and daemon-gate call path. A full real-time lockout cycle was not run against the user's daemon.

**Fix:** retain a successfully verified manual secret for the current host connection in memory, or require explicit HTTP authorization before polling. Stop automatic retries on `badSecret` and `lockedOut` until credentials change or the user explicitly retries. Do not persist a manual secret without the user's storage choice.

### 3. P2: concurrent session creation exceeds `max_sessions`

**Location:** `crates/landlined/src/session.rs:263-270`.

The capacity check runs under a shared read lock, and the pending reservation is incremented after that lock is released. Several creators can all observe capacity before any increments `pending`. An atomic counter does not make this check-then-increment sequence atomic.

**Observed:** the first reproduction round created **10 sessions with `max_sessions = 1`**, using 16 synchronized callers and unmodified production logic. The reproduction killed all created children and waited for registry cleanup before asserting.

**Impact:** reconnect or attach bursts exceed the configured resource limit, each adding a shell, PTY, buffer, and three dedicated threads.

**Fix:** reserve capacity while holding an exclusive registry lock, release that lock before spawning, and transfer the reservation to a registered session consistently. A semaphore permit held throughout a session's lifetime is another option. Add a concurrent creation test that checks the actual count.

### 4. P2: layout events send forbidden frames during unlock

**Location:** `ios/Landline/UI/TerminalScreen.swift:935-938`; `ios/Landline/Net/Connection.swift:181-190`; `crates/landlined/src/server.rs:377-379`.

The terminal's resize callback always sends `RESIZE`. `Connection.send()` allows arbitrary frames while connecting, attaching, and waiting for an unlock. During the unlock exchange, the daemon accepts only `UNLOCK` and closes with protocol error 1002 for a resize or keystroke.

**Observed:** a Swift probe compiling the actual `Connection.swift` and `Frame.swift`, with a fake transport and minimal host fixture, entered `needsUnlock(attemptsLeft: 10)`. A resize then produced frame types `[3, 2]` (`ATTACH`, `RESIZE`) before any unlock. The daemon's rejection branch is explicit.

**Impact:** rotating the device, changing the terminal layout, or typing while the unlock prompt is active can terminate the connection instead of completing authentication. Exact visual timing on a physical phone was not tested.

**Fix:** allow frames according to handshake state. Keep current geometry locally, transmit it after `ATTACHED`, and drop user input until live. Do not replay queued keystrokes into the eventual shell. Add tests for resize and stdin during attaching and unlock.

### 5. P2: fetched files are buffered in iPhone memory without a size limit

**Location:** `ios/Landline/Net/HostAPI.swift:119-132` and `217`.

`fetchOffer()` calls `send()`, which calls `request()`, which uses `URLSession.data(for:)`. The entire response is retained as `Data` before being written to a temporary file. Writing it to disk afterward does not make the transfer streamed. The daemon deliberately imposes no outbox file-size ceiling and now streams its side of the response.

**Trigger:** offer a large archive or disk image with `landlined send`, then fetch it on the phone.

**Impact:** memory consumption grows with file size and a sufficiently large transfer can cause iOS to terminate the app, interrupting the user's terminal session view. No deliberate memory-exhaustion test was performed.

**Fix:** use a download task that writes directly to a temporary file, validate the response, and move the downloaded file into its offer directory. Preserve the existing one-time expired-token retry and clean up failed downloads. Verify with a file substantially larger than the intended memory budget.

### 6. P2: Homebrew formula publication races bottle publication

**Location:** `.github/workflows/release.yml:339` and `370-381`; related formula write at `276`.

`homebrew-push` and `bottle` both follow `homebrew-formula`. `bottle-publish` depends only on `bottle`, then clones the remote tap and merges bottles into whatever formula it finds. There is no dependency ensuring that the new formula has been pushed first.

**Trigger:** the formula push is slow, fails transiently, or is rerun after bottle publication. Bottle publication may read an older formula; alternatively, a later formula push can overwrite the completed bottle block with the bottle-free rendered artifact. Concurrent pushes can also fail without a retry.

**Impact:** the release can finish with a stale formula, rejected merge/push, or missing bottle metadata despite successfully built bottles.

**Evidence:** confirmed from the workflow dependency graph and both complete write paths. No release or remote tap was modified or published during this audit.

**Fix:** keep bottle building independent of the tap secret, but use a single final tap writer that combines the rendered formula artifact with bottle metadata. If retaining separate writers, explicitly order them, use the rendered artifact as the merge input, and handle retry/concurrent release behavior.
